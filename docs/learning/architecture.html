Octop 整体架构

单进程自托管多用户多 Agent 平台 · 青色粗线 ①–⑥ 为控制台一条消息的主链路（已用 [TRACE] 日志实测验证）

一条消息的 6 跳（已实测）

  • ① WS user_turn → chat/ws.py：验 token、校验归属、prepare_dashboard_turn
  • ② channel_manager.enqueue：控制台被当作虚拟 IM 渠道，按 thread:<id> 加锁
  • ③ GlobalProcessor.iter_turn_chunks：斜杠命令就地返回，否则组装 harness 请求
  • ④ AgentManager.stream：再加一层 thread 执行锁
  • ⑤ HarnessAgent.stream → LangGraph → LLM / 工具，写 checkpoint
  • ⑥ chunk 经 ws_hub.push_to_thread 回推；收尾写 usage、历史投影，最后发 done

容易误解的设计点

  • • ChannelManager 全进程只有一个，渠道以 tenant_id=agent_id 区分
  • • Cron 不经过 GlobalProcessor：run_in_session + AgentManager.stream
  • • IM 路径 __call__ 和控制台路径 iter_turn_chunks 平行但不相同，改 bug 两边都要看
  • • 对话正文的权威来源是 checkpoint，thread_messages 只是读模型
  • • HITL 待审批记录、turn_active 只存在于内存，重启就丢
  • • 取消（cancel / /stop）会让流正常结束，按成功轮次记账

修改前的红线

  • • 新增 harness 请求参数：放进 configurable，或者先在 ChatRequest 里声明字段
  • • 工作区文件只通过 BackendWorkspace 读写
  • • 用户可见文案在 en/zh 两份 bundle 里同时加；ErrorCode 还要同步补 _DEFAULT_STATUS
  • • DB 改动写成对迁移，并更新版本断言（当前 v18）
  • • async 函数里不做阻塞 I/O；前端时间统一用服务器时区
  • • 交付前 make all 全绿；改了前端再跑 npx tsc -b
